# smzl-okr

将用户提供的 git 提交记录、工作周报碎片或 OKR 草稿，提炼为清晰、可衡量、结果导向的 OKR。

## 输入

用户通常会提供以下任一类内容：
- git 提交记录（含 commit message、PR 标题、变更模块、简要说明）
- 工作汇总（按事项/模块的要点列表）
- 现有 OKR 草稿（口语化、偏待办）

如信息不足以生成可衡量的结果指标，先提 1-3 个澄清问题再生成（例如：基线数据、目标值、统计口径、时间范围）。

## 生成约束

### Objective（目标）
- 优先输出 1 个总目标（必要时可输出多个）
- 仅当该目标确实体现“需要额外努力/产生重大变化/可被感知的方向性提升”时才输出该 Objective
- 若内容仅是常规维护、无明显增量价值，避免硬凑 Objective，改为请用户补充目标背景或影响范围

### Key Results（关键结果）
- 必须尽量可量化：优先使用数字（数量、比例、时延、成功率、覆盖率、故障数、成本等）
- 对自己狠一点：指标清晰、可衡量、有挑战但合理
- 只写结果，不写 to-do：避免“完成/实现/支持/推进/对接/调研”等过程描述
- 直击要点：不模棱两可，不写“提升一些/优化一下/尽量/大幅”
- 控制数量：每个 Objective 3-5 条 Key Results，聚焦最重要的少数产出

## 输出格式

使用标准 Markdown：

```markdown
Objective: <总目标>
- KR1: <可衡量的结果>
- KR2: <可衡量的结果>
- KR3: <可衡量的结果>
```

如存在多个 Objective，按以下形式分段输出：

```markdown
Objective: <目标A>
- KR1: ...
- KR2: ...

Objective: <目标B>
- KR1: ...
```

## 处理步骤（建议执行顺序）

1. 将输入按主题聚类（交付、质量、性能、稳定性、成本、体验、效率、风险等）
2. 提炼可被业务/团队感知的目标表述作为 Objective（不满足约束则不输出并提出问题）
3. 将每个主题的“做了什么”改写成“带来了什么结果”，并补齐可量化指标口径
4. 对 KR 去重合并，确保互相独立且可验证

## 示例

### 示例输入（git 提交片段）

- feat: 新增订单导入接口，支持批量校验并落库
- fix: 修复导入超时问题，分页改为游标
- chore: 增加关键链路监控与告警规则

### 示例输出

```markdown
Objective: 将订单导入能力提升为可规模化、可观测、稳定可用的交付能力
- KR1: 单次导入 10 万条数据的成功率达到 ≥ 99.9%
- KR2: 导入全链路 P95 耗时降低至 ≤ 5 分钟（以 10 万条为统计口径）
- KR3: 导入相关告警误报率降低至 ≤ 5%，且关键故障发现时间（MTTD）≤ 5 分钟
```
